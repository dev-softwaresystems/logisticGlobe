# Diseño productivo parametrizado — preparado, sin despliegue

Región, cliente, dominio, presupuesto y retención están pendientes. Parámetros por aprobar: al menos dos zonas y dos API; CPU/memoria según perfil; pool por réplica multiplicado por réplicas dentro del presupuesto de conexiones SQL; mínimos/máximos de autoscaling; Redis con TLS/autenticación; MongoDB aprobado; RDS Multi-AZ/PITR; referencias de Secrets Manager/KMS; digest de imagen y orígenes permitidos. La fase actual no incluye apply de IaC ni SDK cloud dentro del dominio.

Topología propuesta: React/CDN → balanceador TLS → API modular ECS/Fargate con readiness. RDS mantiene transacciones, MongoDB histórico GPS y ElastiCache cache, Socket.IO y rate limiting compartido. El adaptador SQS/SNS se materializa cuando se apruebe esa fase, con DLQ, redrive, deduplicación y retención. SQL outbox y contratos permanecen independientes de AWS. API Gateway solo se incorpora si lo requiere la topología; CloudWatch, Secrets Manager y KMS usan mínimo privilegio IAM.

SLI propuesto sobre 30 días: proporción de requests válidos de dashboard, envíos, inventario y flota respondidos correctamente dentro del timeout acordado. Fallan 5xx/timeouts y 429 causados por incapacidad de atender el perfil aprobado. Se excluyen 4xx esperados. El mantenimiento cuenta salvo acuerdo explícito; degradación GPS cuenta para la operación afectada. Sondas externas de solo lectura desde varias zonas usan una identidad sintética. Un objetivo de 99.9% equivale a 43.2 minutos de error en 30 días: todavía no está medido ni acordado.

Despliegue propuesto: revisión y gates, digest/SBOM, referencias a secretos, PITR saludable, migración aditiva como job explícito. Canary 10→25→50→100% con ventana acordada. Abortar por P1, consumo de presupuesto de error, memoria/pools o backlog. Rollback al digest previo y configuración versionada, con estrategia expand/contract; evitar resets y migraciones inversas destructivas.

La alarma de routing propuesta usa el p95 del adaptador provider, que incluye Redis, fetch y escritura de cache; no mide el motor interno. CTO y cliente deben resolver métrica HTTP/motor/adaptador, dataset, mezcla hit/miss y ventana. Un proveedor regional, hosting propio o fallback manual visible requieren presupuesto y aceptación. Runbooks: [recuperación](recovery-plan.md), [alertas](alert-rules.md) y [relevo](devsecops-handover.md).
